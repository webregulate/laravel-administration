Introduces the package-owned WRLABaseUserData model and the generated application model WRLAUserData. Applications inherit maintained defaults and override only their custom behaviour, rather than keeping a full copy of a generated model that can drift between releases.

Breaking Changes

  • Composer constraint: ^0.8 does not allow 0.9.0. Deliberately update your constraint to ^0.9.0 when upgrading.
  • Model names: the generated application model is now App\Models\WRLAUserData in app/Models/WRLAUserData.php, replacing App\Models\UserData. Its package base is WebRegulate\LaravelAdministration\Models\WRLABaseUserData in src/Models/WRLABaseUserData.php. Update model filenames, class declarations, imports, static calls, type hints and the published models.wrla_user_data configuration together. There is no automatic class alias or project-wide rename.
  • Model inheritance: new installations generate an empty WRLAUserData subclass of WRLABaseUserData. Existing models are not overwritten or automatically converted; standalone models continue to work while configured, but do not inherit future fixes. Migrate explicitly to adopt the maintained implementation and new naming convention.
  • Override signatures: when converting an old generated model, retained overrides must be compatible with the base model. Missing or incompatible return types can cause a PHP fatal error when loading the subclass. Do not simply change the parent while leaving the entire old implementation in place.
  • Database connection: the new base no longer contains a connection name copied from DB_CONNECTION at installation time. It uses an explicit model connection first, then wrla_user_data.connection, then Laravel's default connection. Preserve your old connection explicitly if it differs from the current default. User creation no longer replaces an explicit model connection with a configuration value.
  • Custom helper behaviour: inherited password checking now honours getUserByEmail() and getPasswordField() overrides. The getByEmail() alias delegates to getUserByEmail(). User creation now uses the configured model's password-field and password-hashing methods; inherited models also use attachUser() instead of hard-coded attachment.
  • Navigation conditions: enabled-condition callbacks now receive user data from the configured model rather than always using App\Models\UserData. Applications using a different configured class should review these callbacks.

Recommended Model Migration

  1. Install v0.9.0 before referencing WRLABaseUserData. Review and back up your existing application UserData model and published configuration.
  2. Compare your current methods and properties with the package base. Identify intentional customisations, including connection, avatar URLs, authentication, names and permissions. Remove unchanged copied defaults, not project-specific behaviour.
  3. Rename app/Models/UserData.php to app/Models/WRLAUserData.php, rename its class to WRLAUserData, and extend WRLABaseUserData as shown below. Preserve the application namespace, or update the configuration to match a custom namespace.
  4. Replace all application references to App\Models\UserData and UserData:: with the new application class, including imports, type hints, callbacks, tests and custom relationships. Update any old BaseUserData import alias or parent declaration to the actual package class WRLABaseUserData.
  5. Change only the wrla_user_data entry inside your published models array to App\Models\WRLAUserData::class. Do not force-republish the configuration or replace its custom User model and other settings.
  6. Retain only custom overrides, matching the base signatures. Preserve custom table, connection, fillable fields, casts, scopes, traits, boot hooks and relationships where needed. If you override a boot method, call the parent where required by Eloquent.
  7. Run composer dump-autoload and php artisan optimize:clear after the rename to refresh autoloading and cached configuration. Validate login, MFA, user creation/editing, permissions, settings/data, profile avatars, navigation and any project-specific overrides before deploying. Inherited defaults will then receive future package fixes automatically.
<?php

namespace App\Models;

use WebRegulate\LaravelAdministration\Models\WRLABaseUserData;

class WRLAUserData extends WRLABaseUserData
{
}

Do not delete your customised model and rerun the installer as a migration shortcut. The installer preserves an existing WRLAUserData model. If the configuration still points at an existing legacy App\Models\UserData, it leaves that model intact and reports the required migration rather than generating an unused replacement. The table wrla_user_data, relation wrlaUserData, configuration keys and WRLAHelper::getUserDataModelClass() remain unchanged. There is no schema change or data migration required for the class rename or inheritance itself.

Preserving Custom Avatar URLs

The package default retains the current stub's root-relative stored-avatar URL. If your application uses Laravel's asset() helper for a CDN or ASSET_URL, retain that difference as a small override. Delegating the placeholder to the parent keeps future default improvements. 

public static function getAvatarStatic(?string $avatar, ?string $fullName = null): string
{
    if (!empty($avatar)) {
        return asset("storage/images/avatars/$avatar");
    }

    return parent::getAvatarStatic($avatar, $fullName);
}

The inherited getProfileAvatar() calls this override. It retains the current stub's rule that the configured user_avatar callback runs only when a related user exists. Preserve a custom getProfileAvatar() override if your application intentionally differs.

Connection Configuration

Merge this optional block into your published configuration without force-republishing it. Leave it null to use Laravel's default connection, or set a configured Laravel connection name before a fresh installation's migrations. Models and fresh user-data migrations use this setting. 

'wrla_user_data' => [
    'connection' => null,
],

To preserve an old model's fixed connection, retain its property in your application subclass, for example protected $connection = 'mysql';. This property and setConnection() take precedence for model operations; the migration uses the configuration setting instead. Ensure the table exists on the connection you choose. Existing tables and previously published migrations are not rewritten, moved or rerun; coordinate any database move separately and preserve the migration connection when rolling back.

New Features

  • Added the package-owned WRLABaseUserData Eloquent model containing the existing stub's permissions, settings/data, MFA, authentication, avatar, identity and relationship defaults.
  • The renamed WRLAUserData.stub generates an empty WRLAUserData application subclass, leaving all default behaviour maintained by WRLA.
  • Added consistent runtime connection selection for the inherited model, relationships, commands and fresh user-data migrations.

Changes & Improvements

  • Replaced fixed-class calls with late static binding for current-user lookup, avatar generation and password/email helpers, so application overrides are honoured by inherited methods.
  • Removed the application-specific ?User return type from the package implementation. The default still uses Laravel authentication, while overrides may support other user implementations.
  • Kept the application model configurable throughout WRLA, including navigation enabled conditions. No inheritance requirement is enforced against legacy standalone models.
  • The installer reports successful generation or preservation of an existing model and points existing installations to these migration notes. Uninstallation targets WRLAUserData.php; the old UserData.php is included only when it is still the configured WRLA model, avoiding removal of unrelated application models.
  • User creation respects configured password helpers and, for base-model subclasses, attachUser(). Legacy standalone models retain direct user-ID assignment; both paths use the configured user-ID builder.
  • The base model's attachUser() stores the user as an Eloquent relation rather than a database attribute, so attaching a user before saving does not attempt to insert a nonexistent user column.

Keeping Customisations Compatible with Future Updates

  • Do not edit vendor files or copy the base implementation into the application. Inherit unchanged defaults and keep overrides narrowly focused.
  • Call parent::methodName() to extend default behaviour, and use static::methodName() for overridable static calls inside custom code.
  • Use your configured application class or WRLAHelper for application calls; do not replace the configured subclass with the package base and bypass customisations.
  • Treat overridable signatures as the extension contract. Review release notes and validate retained overrides whenever upgrading; an override replaces its parent implementation and does not automatically receive changes to that method.
  • Custom authentication still requires compatible Laravel user/guard configuration or an attemptLogin() override. Changing getPasswordField() alone does not reconfigure Laravel's login provider or password-reset flow; those continue to use the configured user model and existing routes.
