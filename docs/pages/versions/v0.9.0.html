WRLAUserData now inherits WRLA's defaults. Keep only your custom overrides.

Breaking Changes

  • UserData becomes WRLAUserData, extending WRLAUserDataBase.
  • Custom overrides must match the base method signatures.

Upgrade Steps

  1. Set WRLA's Composer constraint to ^0.9.0 (keep your existing constraint for local development), then run: 
    composer update webregulate/laravel-administration
  2. Rename app/Models/UserData.php → app/Models/WRLAUserData.php.
  3. Project-wide replace: \bUserData\b → WRLAUserData. Enable regex + case-sensitive; application PHP only, not vendor/caches. Preview matches before replacing.
  4. Replace the model with this. Retain your namespace, custom or overriden methods/properties: 
    <?php

namespace App\Models;

use WebRegulate\LaravelAdministration\Models\WRLAUserDataBase;

/**
 * Model: WRLAUserData
 *
 * @property int $id bigint unsigned
 * @property string $user_id varchar(255)
 * @property string $avatar varchar(255)
 * @property string $permissions json
 * @property string $settings json
 * @property string $data json
 * @property string $mfa_secret varchar(255)
 */
class WRLAUserData extends WRLAUserDataBase
{
}
  5. Run, then check login and your overrides: 
    composer dump-autoload
php artisan optimize:clear

No database changes. Table, relation and helper names stay unchanged. The installer does not migrate existing models.

New Features

  • Package-owned WRLAUserDataBase contains the default implementation.
  • New installations generate an empty WRLAUserData subclass. Override only what your project needs; leave defaults inherited to receive future fixes.

Changes & Improvements

  • Inherited static calls honour application overrides, and WRLA resolves the configured application model rather than a hard-coded class.
  • The installer and uninstaller use the renamed application model while recognising configured legacy models.
  • User creation and password checks honour model helpers. Connection priority: model, config, Laravel default; review this order if using custom connections.
  • The generated User model's ENABLED and DELETE defaults now use belongsToUser() to check the active model against the current user's data. Masters can manage users, and other users can access their own profile; deletion requires a master and excludes their own account. 
    static::setPermission(ManageableModelPermissions::ENABLED, fn($wrlaUserData) => $wrlaUserData->isMaster() || $wrlaUserData->belongsToUser(WRLAHelper::getActiveModelInstance()));
static::setPermission(ManageableModelPermissions::DELETE, fn($wrlaUserData) => $wrlaUserData->isMaster() && !$wrlaUserData->belongsToUser(WRLAHelper::getActiveModelInstance()));
    Existing applications must update these permissions manually, preserving any custom restrictions.
