Cacheable configuration and application-owned runtime settings, with a consent-based upgrade command.

Breaking Changes

  • config/wr-laravel-administration.php becomes config/wrla.php. Config lookups now use wrla.*.
  • Every runtime-capable setting belongs exclusively in App\WRLA\WRLASettings::runtime(): array, including its boolean/null/list values. The generated method includes all runtime options. The nested keys stay the same.
  • Custom code reading callback-capable settings must use WRLASettingsService::get() rather than reading only Laravel config. Existing WRLA helpers already use the resolver.
  • Feature access rules live in runtime(), including file_manager.enabled, logs.enabled and documentation.enabled. Each accepts a boolean or callback receiving WRLA user data. Viewer selection, filesystem definitions and other static options stay in config.
  • File Manager, Logs, Scheduler and Schema Viewer enforce runtime access on initial page loads and every Livewire request. The standalone Opcodes viewer uses logs.enabled too, rather than deriving authorization from a navigation item. Move any custom log authorization into that rule; generated log access initially allows masters. Custom navigation can further restrict visibility but cannot bypass feature access.
  • build_wrla_user_data_id must be callable. The generated callback returns the user ID; invalid values no longer silently fall back to it.
  • Asset paths, Blade view namespaces and route names are unchanged. No database changes are required.

Upgrade Locally First

Start with a clean Git worktree: no staged, unstaged or untracked changes. The upgrade warns you before applying changes and does not create backup copies. We recommend running it locally and agreeing to the automatic migration after reviewing its file preview. Review the automatically applied changes in Git and test your application before finalising the upgrade, committing or deploying.

  1. Change your Composer constraint to ^0.10.1 (keep an appropriate existing constraint when developing from a local checkout), then update: 
    composer update webregulate/laravel-administration
  2. Run from a local terminal, review the preview and confirm when ready: 
    php artisan wrla:upgrade
    The command lists affected files and asks before writing. Declining leaves source files unchanged. It does not update Composer dependencies or run database migrations. Optionally add --dry-run for a read-only preview without confirmation or writes, useful for scripts and CI.
  3. Review the renamed config, generated runtime() method and rewritten application references. Test authentication, permissions, developer tools, notifications, avatars, user IDs and any database-browser/scheduler overrides you use.
  4. Confirm config caching works in your application, then clear the local cache when finished testing: 
    php artisan config:cache
php artisan config:clear

Console setup and upgrade commands remain available before runtime settings are complete. Administration requires the complete runtime method; there is no config/default fallback. A closure-filled legacy config is not cacheable. Do not republish config with --force or manually create both config files before upgrading. If both files exist, merge them manually first. Earlier releases' running update commands cannot load this new upgrade step until the new package is installed: run wrla:upgrade explicitly for this first transition.

What the Automatic Migration Does

  • Parses PHP source without requiring config files or executing application callbacks.
  • Moves every runtime-owned setting out of config, retaining imported names, list order and explicit boolean/null/empty values. Missing runtime options are written into the application method from the installation template.
  • Inserts a new runtime() as the first method, followed by one blank line, preserving existing routes and navigation. Existing runtime values take precedence over old config values, preserving their previous effective behaviour.
  • Rewrites standard PHP config helpers, Config facade aliases, repository getters and common Blade expressions. Runtime reads use the resolver; formerly boolean-only feature reads use the access helpers so callbacks are evaluated. Whole-config/mixed parent reads and runtime config assignments require manual migration rather than changing their meaning silently.
  • Preserves Blade templates' existing PHP opening/closing boundaries instead of inserting stray PHP tags around rewritten markup.
  • Scans application PHP and Blade source, excluding vendor, node_modules, public assets, storage and bootstrap caches. It leaves Blade namespaces and public asset URLs alone.
  • Warns you to start with a clean Git worktree so the resulting diff contains only the automatic upgrade changes. No backup copies or upgrade manifests are created. An exclusive lock prevents concurrent upgrades, and stale previews cannot overwrite new edits. Originals are held in memory for rollback on write failures; any rollback error is reported for manual recovery using Git.
  • Clears config, route and compiled-view caches after a successful migration. Running the command again is safe and reports when nothing remains to migrate.

Computed keys, captured file-scope state, custom runtime logic, config conflicts and linked paths may need manual work. When a detected case cannot be migrated safely, the command stops before applying the plan and explains why. Review custom wrappers, namespace strings held in variables, code outside the scanned application, and any dynamically generated references manually; static analysis cannot discover every indirection. If you have already run an earlier upgrade, run it again to move the remaining feature access rules, add the explicit log access rule and correct older generated settings comments. Existing configured booleans and callbacks are retained; review the new log access rule against your application's requirements. To undo a completed upgrade, review and revert its tracked changes using Git, remove only files newly created by the upgrade, then clear config/routes/views. In-memory rollback cannot recover from a terminated process or a later failed application test; the clean Git worktree is your recovery point.

Runtime Settings

Keep scalar-only options in wrla.php. The generated runtime() is the sole source for every runtime-capable option. Edit its existing sections, keeping all other generated settings. For example: 

'user_avatar' => fn ($user) => $user->profile_image,
'scheduler' => [
    'enabled' => fn ($wrlaUserData) => $wrlaUserData?->isMaster() ?? false,
    'can_run_adhoc' => null,
],

There are no package runtime defaults or config fallbacks at read time. Missing required options fail clearly; run the local upgrade command to add them explicitly. Explicit false, null and empty lists are respected. Required permission maps include every action. Callback definitions are built once per request; the resolver does not evaluate them or cache their results. Keep user lookups and database queries inside the callbacks, not at the top of runtime(). The initial generated access rules allow admins for manageable models and masters for developer tools, File Manager, Logs and documentation links. Documentation page access initially allows all authenticated WRLA users. See Configuration for every supported runtime key.

Updates and Automation

From this release, wrla:update runs Composer, launches wrla:upgrade in a fresh PHP process, then clears application caches. Interactive terminals forward confirmation input. Web/non-interactive updates never silently approve source edits: pending migrations return a non-zero status and tell you to run the upgrade locally. Explicitly approved automation can use: 

php artisan wrla:upgrade --yes --no-interaction
php artisan wrla:update --yes --no-interaction

Use --yes only after reviewing and testing the migration. New installations publish cacheable config and a complete runtime settings method automatically. Installing or upgrading preserves existing application customizations rather than overwriting them.
